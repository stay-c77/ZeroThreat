RECENT FIX: TYPOSQUATTING DETECTION (Duplicate Character Handling)
================================================================================

**Problem Found:** gooogle.com (3 o's) was detected as SAFE instead of SUSPICIOUS
**Root Cause:** The brand similarity check was using deduplicated strings, which removed the extra 'o', making it too similar to match.

**Solution Implemented:**
- Changed from deduplicated Levenshtein distance to DIRECT distance
- Now detects single character differences (even duplicates) as suspicious
- Examples that now correctly trigger detection:
  ✓ gooogle → google (extra 'o') = SUSPICIOUS
  ✓ netflixx → netflix (extra 'x') = SUSPICIOUS
  ✓ ammazon → amazon (extra 'm') = SUSPICIOUS
  ✓ paypall → paypal (extra 'l') = SUSPICIOUS

**Detection Thresholds:**
- Distance = 1 (single char difference) → 32 points (SUSPICIOUS)
- Distance with dedup = 1 (duplicate chars) → 28 points (SUSPICIOUS)
- High similarity (Jaro-Winkler ≥ 0.97) → 36 points (SUSPICIOUS)

**File Modified:**
- PhishingDetector.kt (Brand similarity checking logic)

⭐ ENHANCEMENT: WHITELIST-BASED SIMILARITY CHECKING
================================================================================

**Feature Added:** Typosquatting detection against whitelisted domains
**Why:** Whitelist contains 1000+ legitimate websites, perfect for catching mimics

**New Detection Logic:**
- Compares candidate domain against top 1000 whitelisted domains
- Detects single-character typos of whitelisted sites
- Examples:
  ✓ gooogle.com vs whitelisted google.com → SUSPICIOUS
  ✓ facbk.com vs whitelisted facebook.com → SUSPICIOUS (if facebook in top 1000)
  ✓ netlix.com vs whitelisted netflix.com → SUSPICIOUS

**Scoring:**
- Direct distance = 1 vs whitelist → 35 points
- Jaro-Winkler >= 0.98 vs whitelist → 34 points
- Only triggers if higher than brand score (no double penalty)

**File Modified:**
- PhishingDetector.kt (Added whitelist similarity section)

**Benefits:**
- Catches typos of legitimate sites users trust
- Uses existing whitelist data (no new resources needed)
- Adds 35 points = Triggers SUSPICIOUS easily (10+ threshold)

================================================================================
TECHNICAL IMPLEMENTATION DETAILS
================================================================================

DNS Resolution:
- Uses Java's InetAddress.getByName() for synchronous DNS lookup
- Runs on IO dispatcher to prevent main thread blocking
- Catches UnknownHostException for non-existent domains
- Timeout: Natural OS timeout (~5-30 seconds depending on network)

Coroutines:
- NotificationListener: runBlocking(Dispatchers.IO) for sync DNS check
- SafeBrowserActivity: runBlocking() for sync DNS check in onClick handler
- DnsChecker: suspend function with Dispatchers.IO context

Permission Handling:
- POST_NOTIFICATIONS permission added to AndroidManifest.xml
- Runtime check for Android 13+ (Build.VERSION_CODES.TIRAMISU)
- Uses ContextCompat.checkSelfPermission()
- Graceful degradation if permission not granted (warning logged)

Logging:
- "DnsChecker" tag for DNS resolution events
- "NOTIF_TRACE" tag for notification listener flow
- "CLICK_SCAN" tag for click handler flow
- Comprehensive debug output for troubleshooting

ERROR HANDLING
================================================================================

Scenario: Network timeout during DNS check
→ Treated as non-existent domain (75% suspicious)
→ Shows warning to user

Scenario: POST_NOTIFICATIONS permission denied on Android 13+
→ Gracefully degraded: No notification shown
→ Warning logged: "POST_NOTIFICATIONS permission not granted"

Scenario: Invalid URL format
→ DnsChecker returns score: 50 (moderate suspicion)
→ Message: "Invalid URL format"

Scenario: DNS exception (non-UnknownHostException)
→ Treated as error (50% suspicion)
→ User can still proceed with Continue button

================================================================================
PERFORMANCE CONSIDERATIONS
================================================================================

⚠️ IMPORTANT: DNS lookups can block the notification listener thread!
- Current implementation uses runBlocking() on main flow
- DNS timeout is OS-dependent (typically 5-30 seconds)
- Solutions for production:
  Option 1: Use timeout mechanism (wrapped coroutine with withTimeout)
  Option 2: Cache DNS results for frequently accessed domains
  Option 3: Move to background service with LocalBroadcast

Current status: Synchronous DNS check for reliability, not optimized for speed

================================================================================
KNOWN LIMITATIONS
================================================================================

1. DNS Resolution Timeout:
   - No explicit timeout (uses OS default)
   - May cause notification listener to be unresponsive briefly
   - Recommended fix: Add timeout wrapper

2. False Positives:
   - Networks with DNS filtering may show false non-existent
   - Workaround: User can click "Continue Anyway"

3. Cache:
   - No caching of DNS results
   - Each URL re-checked every time
   - Recommended: Implement LRU cache for common domains
